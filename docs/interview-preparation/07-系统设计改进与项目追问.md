# 07｜系统设计改进与项目追问

> **Reliability Update · 2026-08-24**
>
> 商品目录 → Stripe 的双写、失败重试、版本乱序和漂移风险已经形成可运行实现。本章风险分级相应拆成“Catalog 已修复”和“Payment → Order 待修复”，避免把同一个可靠性结论泛化到不同事务边界。

## 学习目标

- 能主动识别项目风险，不被面试官追问后才承认问题。
- 能按业务影响排序，而不是一上来堆微服务中间件。
- 掌握支付、库存、消息、缓存和服务故障的分析框架。

建议耗时：**1 小时**。

## 1. 先给项目做风险分级

### P0：交易正确性与安全

| 风险                           | 当前情况                                                                                                                | 改进                                                                      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 商品 DB 成功但 Stripe 未同步   | **已修复（当前分支）**：Product Outbox → Payment Inbox/ledger → Stripe worker → result Outbox；带版本、幂等、重试和对账 | 上线时按 `migration.md` 回填、清零 drift 后再开启强制可售，并持续监控积压 |
| 重复 Webhook/消息产生重复订单  | 无 Stripe event ID 去重                                                                                                 | `provider_event_id` 唯一约束 + 幂等处理记录                               |
| 支付成功但事件/订单丢失        | Kafka send 未 await，consumer 吞异常                                                                                    | await + Outbox/可靠 retry + 对账                                          |
| 无库存模型，可能售卖不可用商品 | 未实现 SKU/库存                                                                                                         | SKU + inventory + 预占/条件更新                                           |
| 事件价格与订单快照可信边界     | Checkout 从 Payment DB 读取版本确认的 Stripe Price ID，并忽略客户端名称/价格                                            | 再校验 SKU 可售、数量上限、货币；订单关联支付 ID                          |
| 后端输入校验不统一             | 部分 Controller 只做手工检查                                                                                            | schema/DTO 全量验证、统一错误码                                           |
| 管理权限只依赖粗角色           | user/admin claims                                                                                                       | permission + 资源/动作授权 + 审计                                         |

### P1：可恢复性与可观测性

- Catalog 已有 event ID/key/version、Inbox/Outbox、Stripe retry 与定期对账；仍需补 catalog DLQ/更完整指标。
- Payment → Order 仍需 Webhook Inbox、Payment Outbox、Order Inbox、retry topic、DLQ 与跨账本对账。
- request/correlation ID、结构化日志、指标、trace、告警。
- 所有外部调用设置 timeout；重试只覆盖安全且可幂等的瞬时失败。
- 优雅停机与 readiness/liveness 分离。
- API 统一错误协议、契约和版本策略。

### P2：性能与规模

- Next.js 公共商品缓存与 tag revalidation。
- PostgreSQL/MongoDB 索引和服务端 cursor 分页。
- Redis 商品缓存、限流、统计缓存。
- CDN/Cloudinary 图片变换、bundle 分析和 Web Vitals。
- 根据真实指标决定读副本、分片、服务扩容或搜索引擎。

优先级原则：**先不丢钱、不越权、不重复；再可发现、可恢复；最后才是规模优化。**

## 2. 生产化支付订单设计

### 推荐状态机

```text
Order: pending_payment → paid → fulfilling → shipped → completed
                         ↘ cancelled / refunding → refunded

Payment: created → processing → succeeded
                    ↘ failed / cancelled / refunded
```

状态转换必须单向且幂等。例如已 `paid` 的订单再次收到相同成功事件，返回成功但不重复扣库存/发货。

### 推荐链路

1. 服务端基于 SKU 创建 `pending_payment` 订单，并在事务中预占库存。
2. 使用订单号作为 Stripe metadata/client reference，金额由服务端计算。
3. 保存 Checkout Session/Payment Intent ID，建立唯一约束。
4. Stripe Webhook 验签，先按 event ID 幂等落 `payment_events`。
5. 同一数据库事务更新 payment/order、确认库存、写 Outbox。
6. Outbox 发布 `order.paid`，通知履约、邮件等下游。
7. 定时对账 Stripe 与本地 payment；过期订单释放库存。

如果订单数据库保持 MongoDB，也可以使用单订单文档原子状态更新 + 唯一 event collection；但库存若在 PostgreSQL，会形成跨库 Saga。对当前规模，更简单的选择是把订单、支付、库存放入同一 PostgreSQL 事务边界，订单项仍保存 JSONB/关系快照。

## 3. 故障分析模板

面试官问“服务挂了怎么办”时，不要只回答重试。按以下顺序：

1. **故障点**：浏览器、服务、DB、Kafka、Stripe、Redis、网络？
2. **是否完成**：请求超时不等于失败，副作用可能已经发生。
3. **幂等性**：再次执行会不会重复扣款/下单？
4. **持久记录**：是否有 event ID、状态、Outbox、审计日志可判断？
5. **恢复方式**：自动 retry、DLQ、补偿、对账、人工重放？
6. **用户体验**：明确处理中状态，前端轮询/刷新结果，不误导再次支付。
7. **可观测性**：哪些指标和告警能发现？

## 4. 高频系统设计场景

### 场景 A：用户点击支付后页面超时

- 不立即显示“支付失败”；返回/展示 processing。
- 前端使用 session/order ID 查询服务端权威状态。
- 重试创建 Session 时使用 idempotency key，防重复创建。
- 最终状态以 Stripe Webhook/主动查询为准。
- 定时任务对账长时间 processing 记录。

### 场景 B：Stripe 重复发送 Webhook

- 验签后按 Stripe `event.id` 插入唯一记录。
- 唯一冲突直接返回 2xx，表示已处理。
- 状态机更新带前置条件，避免倒退。
- Webhook 尽快确认；重业务转入可靠异步链路。

### 场景 C：Kafka 消费订单事件时 MongoDB 短暂不可用

- handler 抛出可重试异常，不能吞掉后提交 offset。
- 指数退避，超过次数进入 retry topic/DLQ。
- event ID 唯一，恢复后重复消费不会建重复订单。
- lag、retry、DLQ 告警；恢复后受控重放。

### 场景 D：热门商品详情流量突增

- CDN 缓存图片；Next.js Data Cache/Redis 缓存公共商品数据。
- TTL 抖动 + singleflight 防击穿。
- Redis 故障快速降级，但对数据库限流保护。
- 数据库索引与连接池容量验证。
- 先看 p95/p99、cache hit rate、DB CPU/连接数，再决定扩容。

### 场景 E：两个用户同时买最后一件商品

- 不能依赖前端库存或“先查再减”。
- 数据库条件 UPDATE `available >= qty` 或行锁。
- 支付前预占，设置过期；支付成功确认，失败/超时释放。
- 所有操作按 order/variant 幂等，定期修复过期 reservation。

### 场景 F：Redis 缓存与数据库不一致

- 数据库是权威源；写 DB 后删除 cache。
- TTL 限制不一致窗口，关键读绕过缓存。
- 失效失败通过 Outbox/CDC 重试。
- 监控缓存命中、回源、旧数据投诉；必要时版本化 value。

## 5. API 与服务治理

### API 契约

- 输入 DTO/schema、输出 DTO、错误 code 和 HTTP status 统一。
- HTTP：OpenAPI；事件：JSON Schema/Avro/Protobuf + 兼容检查。
- 分页、时间、金额、ID、空值语义统一。
- 不把 ORM Entity 直接当公共契约。

### Timeout、Retry、Circuit Breaker

- 每个外部调用必须 timeout，否则资源会被无限占用。
- 只重试瞬时错误；写操作必须幂等；指数退避 + jitter + 上限。
- Circuit Breaker 在下游持续故障时快速失败，保护线程/连接池。
- Bulkhead 隔离不同下游资源，避免 Stripe 故障拖垮商品读取。

### 健康检查

- Liveness：进程是否需要重启，不应因短暂下游故障频繁重启。
- Readiness：是否能接新流量，可检查关键依赖/初始化。
- Startup：启动慢服务完成初始化前避免被探活杀死。

当前 `/health` 主要返回进程存活信息，更接近 liveness；尚不能证明 DB/Kafka 已可工作。

## 6. 可观测性

### Logs

结构化 JSON，至少包含：timestamp、level、service、environment、requestId、traceId、userId（按隐私规则）、route、errorCode、duration。Token、密码、完整地址和支付敏感数据不得入日志。

### Metrics

使用 RED：Rate、Errors、Duration；资源使用 USE：Utilization、Saturation、Errors。业务指标还包括 Checkout 创建/成功率、Webhook 延迟、订单创建差值、库存预占超时和 Kafka lag。

### Tracing

通过 OpenTelemetry 传播 trace/correlation ID，HTTP header 和 Kafka event header 都要携带。Trace 用于跨 Next.js → Payment → Stripe/Kafka → Order 定位长尾与失败。

### Alert

告警必须可行动。例如“5 分钟支付成功事件数显著高于订单创建数”，比单纯 CPU 80% 更贴近业务损失。

## 7. 安全与部署基础

- Secret 放 secret manager，不写入镜像、前端 `NEXT_PUBLIC_*` 或日志。
- Kafka 生产启用 TLS/SASL/ACL，当前本地 PLAINTEXT 仅适合开发。
- 服务只暴露需要端口，数据库不直接公网开放。
- 依赖扫描、容器非 root、最小权限、Webhook secret 轮换。
- 数据库迁移与应用发布采用兼容的 expand/contract。
- 灰度/滚动发布期间，新旧服务必须兼容事件和 API。

## 8. 三阶段演进路线

> **Reliability Update · 2026-08-24：** 商品目录这一条纵向链路已完成第一、二阶段的核心正确性与恢复机制；下面的剩余优先级集中在支付订单、库存和系统级观测。

### 第一阶段：把正确性补齐

- Webhook event ID 唯一、订单/支付状态机。
- SKU/库存与服务端金额校验。
- 以 Catalog 实现为参考，让 Payment → Order 使用 Outbox/Inbox、消费异常正确传播和消费者幂等。
- DTO/schema、统一错误、安全日志脱敏。

### 第二阶段：让系统可恢复、可观察

- 为 Payment → Order 增加 retry/DLQ 和 Stripe payment/payment DB/Order 对账；将 Catalog worker/Outbox 积压纳入指标告警。
- request/trace ID、结构化日志、指标与业务告警。
- timeout、有限 retry、优雅停机、readiness。
- 数据库索引、分页与慢查询基线。

### 第三阶段：用数据驱动扩展

- Next.js/Redis 缓存和限流。
- 按真实瓶颈扩实例、读副本、分片或搜索服务。
- 根据团队和发布边界合并/拆分服务；统一主框架与模板。
- 契约测试、故障演练、容量规划和 SLO。

## 9. 面试表达：如何承认项目不足

> 当前项目完成的是完整功能闭环和关键技术验证，不把它包装成已经承载生产流量。商品目录侧已经把 Product/Outbox 原子提交、Payment Inbox、Stripe 幂等 worker、结果回写与对账落到代码，解决的是“数据库提交不等于 Stripe 成功”这一条边界；支付 Webhook 到订单仍缺 event ID 去重、Payment Outbox、Order Inbox 和库存事务。我会复用已验证的可靠性模式补下一条交易链，再完善可观测性，最后依据指标引入 Redis 或扩容。
