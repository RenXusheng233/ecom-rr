## 一、项目与架构

### 1. 请介绍这个项目

关键词：Next.js 16、两个前端、四个领域服务、PostgreSQL/MongoDB、Kafka、Clerk、Stripe、完整交易链、生产化边界。

参考 [项目介绍模板](./00-一周学习路线与项目介绍.md#3-项目介绍模板)。

### 2. 为什么使用 Turborepo Monorepo？

> 多应用共享 TypeScript 类型、Kafka 工具、数据库客户端、ESLint 和 tsconfig；pnpm workspace 统一依赖，Turborepo 管任务依赖与缓存。收益是跨包变更一致、复用和 CI 提速；成本是构建边界、版本耦合和权限需要治理。项目规模较小时 Monorepo 比多仓库更容易维护。

### 3. 为什么拆四个服务？

> 按商品、订单、支付、身份领域隔离职责与数据模型，实践同步 HTTP 和异步事件。但当前规模下它也增加一致性和运维成本；真实小团队可先用 NestJS 模块化单体，等团队、发布、负载或合规边界出现再抽取。

### 4. 微服务是否应该共享 `packages/types`？

> Monorepo 内共享编译期类型提升效率，但 TypeScript 类型运行时不存在，也可能让服务同时升级。公共 HTTP/事件契约应有运行时 schema、版本和兼容检查；内部领域 Entity 不应直接共享。共享的是 contract，不是数据库模型和业务实现。

### 5. 当前项目最需要先改什么？

> 商品目录 → Stripe 以及 Webhook → Payment → Order 的 Outbox/Inbox、幂等重试、版本控制、Ack 与对账已经完成。下一优先级是库存/SKU 预占和支付/取消/退款/履约 Saga；然后补 retry topic/DLQ 与可观测性；最后按指标做缓存和扩容。

## 二、Next.js 与 React

### 6. Server Component 和 Client Component 有什么区别？

> Server Component 在服务端执行，不把组件实现发到浏览器，可直接访问后端资源；Client Component 支持 state、effect、事件和浏览器 API，需要 hydration。边界由 `'use client'` 建立，应只把最小交互子树放到客户端。

### 7. RSC、SSR、SSG 是什么关系？

> RSC 解决组件执行与传输边界；SSR/SSG 解决何时生成初始页面。Client Component 也可参与服务端预渲染。不能把 RSC 等同于 SSR，也不能认为用了 RSC 就自动缓存。

### 8. Next.js 16 的 `fetch` 默认缓存吗？

> 当前官方文档中服务端 `fetch` 默认是 auto no cache；静态预渲染时行为还受 route 动态性影响。要明确使用 `force-cache`、`no-store` 或 `next.revalidate/tags`。本项目没有显式缓存配置，因此不能宣称商品页已实现 ISR。

### 9. `revalidatePath` 与 `revalidateTag` 区别？

> Path 按页面失效，简单但范围较粗；Tag 按数据实体/集合失效，适合同一商品被首页、列表、详情复用。商品更新可同时使 `product:42` 和 `products` 失效。

### 10. 如何优化商品详情 SEO？

> 服务端输出商品内容；`generateMetadata` 生成唯一 title/description/OG；canonical 合并规格 query；Product JSON-LD；sitemap/robots；删除商品返回 404；优化主图 LCP、移动体验和内部链接。

### 11. 如何定位 Next.js 页面慢？

> 先分服务端 TTFB、网络资源、客户端主线程和数据库/下游。看 Server Timing/trace、Network waterfall、React Profiler、Performance、Web Vitals 和 bundle analyzer。先消除串行 I/O 和慢查询，再缩 client boundary、图片和 bundle，最后缓存。

### 12. Zustand 和 React Query 有何区别？

> Zustand 管客户端拥有的跨组件状态，如购物车；React Query 管远程服务端状态，包括请求、缓存、重试与失效。URL 可分享状态放 search params，表单用 React Hook Form，不能把所有状态塞进一个全局 store。

### 13. Zustand persist 有什么风险？

> hydration 前后状态可能不一致；localStorage 可被用户修改且包含旧数据；多 tab 同步需要处理；敏感信息不能存。项目购物车只用于 UI，支付服务从 Payment DB 读取版本确认的 Stripe Price ID，并忽略客户端名称和价格，这是必要的可信边界。

### 14. shadcn/ui 与传统组件库有什么区别？

> shadcn/ui 把组件源码加入项目，基于 Radix 等原语，定制自由且无封闭运行时包；代价是升级、可访问性验证和一致性由团队承担。传统库统一升级和 API 更稳定，但深度定制受限制。

## 三、认证与安全

### 15. Clerk 相比自研有什么优势和劣势？

> 优势是登录、OAuth、MFA、Session、安全维护和 UI 快速交付；劣势是供应商锁定、随规模成本、数据合规和深度定制。选择要比较总拥有成本，不只比较 SaaS 单价和开发几天。

### 16. Session 与 JWT 怎么选？

> 服务端 Session 易撤销但每次需要共享存储；JWT 验证分散、适合多服务，但 claims 到期前可能陈旧且难撤销。常见组合是短期 Access JWT + 服务端可撤销、轮换的 Refresh Session；BFF 也可让浏览器只持 HttpOnly Cookie。

### 17. JWT 为什么不是加密？

> 常见 JWS JWT 的 payload 只是 Base64URL 编码，签名保证未篡改，不保证保密。敏感信息不应放 payload；仍必须 HTTPS、验证 iss/aud/exp/算法和正确管理密钥。

### 18. JWT 如何实现退出登录和角色立即变更？

> Access Token 短期；撤销 Refresh Session；高风险场景查 session/tokenVersion 或短期 denylist；角色变更后提高版本或让旧 Token 尽快过期。完全无状态和立即撤销不能同时免费获得。

### 19. RBAC 和 ABAC 区别？

> RBAC 基于角色/权限，管理简单；ABAC 结合主体、资源和环境属性，更灵活但规则复杂。项目 admin/user 是 RBAC，用户只能查自己的订单属于资源属性授权。

### 20. 为什么前端路由保护不够？

> 客户端可绕过。Next.js proxy 用于体验和早期拦截，后端每个接口必须验证身份、权限和资源归属；写接口不能信任来自前端的 role、userId、price。

### 21. XSS、CSRF、CORS 分别是什么？

> XSS 是脚本注入；CSRF 利用浏览器自动带 Cookie 发跨站请求；CORS 控制浏览器是否允许页面读取跨源响应，不是认证。分别用转义/CSP、SameSite/CSRF Token/Origin 校验、正确 allowlist 处理。

## 四、Node.js 与 NestJS

### 22. Express、Fastify、Hono、NestJS 如何选？

> Express 通用自由；Fastify schema/插件和性能强；Hono 轻量、Web Standards、多 runtime；NestJS 提供 DI、模块和工程治理。选型先看团队和维护，再看运行环境与性能数据。我的主栈选择 NestJS，性能敏感可配 Fastify adapter。

### 23. Node.js 适合什么，不适合什么？

> 事件循环适合大量 I/O 并发；同步 CPU 重任务会阻塞 event loop。CPU 任务可用 worker threads、独立服务或任务队列。还要避免同步文件/加密、无界 JSON、过多 Promise 和连接池耗尽。

### 24. NestJS 的 DI 有什么价值？

> 依赖显式由容器装配，业务只依赖抽象；可统一生命周期、配置和测试替换。它不会自动带来低耦合，如果 Module 循环依赖、全局 provider 或 Service 职责过大，仍会形成紧耦合。

### 25. Guard、Pipe、Interceptor、Filter 的区别？

> Guard 做准入/授权；Pipe 做参数验证转换；Interceptor 包裹调用前后做日志、响应、缓存、超时；Filter 把异常映射到响应。请求大致是 Middleware → Guard → Interceptor before → Pipe → Controller → Interceptor after，异常进入 Filter。

### 26. NestJS request scope 为什么慎用？

> 每请求创建实例，并会沿依赖链传播 scope，增加 GC 和实例化成本。request ID 等上下文可用 AsyncLocalStorage；大多数无状态 Service 保持 singleton。

### 27. NestJS 如何做事务？

> 事务边界放在 application use case，不让多个 repository 各自 commit。通过 Prisma transaction client/Unit of Work 传入同一上下文；事务内不做长时间第三方网络调用。跨 Kafka/Stripe 使用 Outbox/Saga，而不是假装一个本地事务能覆盖全部。

### 28. 单元测试与 E2E 如何划分？

> 单元测业务分支并替换 repository；集成测真实 DB 查询、事务和 adapter；E2E 启动 Nest app 测 Pipe/Guard/Filter/路由；契约测试保证 HTTP/事件兼容。支付优先测幂等、超时、重复和回滚。

## 五、数据库

### 29. PostgreSQL 与 MongoDB 如何选？

> PostgreSQL 强在关系、事务、约束与复杂 SQL；MongoDB 强在聚合文档和灵活嵌入。选择依据是事务边界、查询路径与约束，不是数据看起来像 JSON。订单涉及支付库存时 PostgreSQL 往往更直接，MongoDB 单订单文档快照也有合理性。

### 30. 什么是 MVCC？

> 多版本并发控制让读者看到符合快照的行版本，减少读写互相阻塞。它需要 vacuum/版本回收，也不消除写冲突、锁、序列化失败或业务竞态。

### 31. 四种隔离级别怎么理解？

> 从 Read Uncommitted、Read Committed、Repeatable Read 到 Serializable，隔离增强、并发成本通常增大。PostgreSQL 默认 Read Committed；Serializable 可能主动中止事务，应用必须重试。具体异常要结合数据库实现，不能只背标准表。

### 32. 乐观锁与悲观锁怎么选？

> 乐观锁用 version/条件更新，适合冲突低；悲观锁 `FOR UPDATE`，适合冲突高且临界区短。库存还可用单条 `UPDATE ... WHERE available >= qty`，通常更简单。两者都要处理失败和重试。

### 33. 什么是组合索引最左前缀？

> B-tree 组合索引按列顺序组织，前导列决定可定位范围。`(user_id, created_at)` 适合按用户再按时间，不一定支持只按时间。范围、排序、选择性与数据库优化器都会影响结果，最终看 EXPLAIN。

### 34. 什么是覆盖索引？代价是什么？

> 查询需要的列都能从索引得到，可能减少回表。但索引更大、写放大更高，且 PostgreSQL 是否 index-only scan 还受 visibility map 等影响。只为高频路径设计，不要把所有返回列都塞入索引。

### 35. 如何防库存超卖？

> 服务端数据库使用带库存条件的原子更新或事务行锁，检查 affected rows；支付流程用库存预占和过期释放；每一步按 order/SKU 幂等。Redis 锁可减竞争，数据库仍是最终约束。

### 36. Prisma、TypeORM、Drizzle 怎么选？

> Prisma schema 与生成类型 DX 强；TypeORM 偏 Entity/OOP 且 Nest 生态成熟；Drizzle 更接近 SQL、抽象轻。都不能替代 SQL、索引和执行计划。常规查询用 ORM，复杂性能路径可用受测试的 query builder/raw SQL，并通过 repository 隔离。

## 六、Kafka

### 37. Partition 与 Consumer Group 的关系？

> group 内一个 partition 同时只分配给一个 consumer，因此并行上限由 partition 数决定；不同 group 各自读取完整数据。扩 consumer 超过 partition 数不会继续提升消费并行度。

### 38. Kafka 如何保证不丢消息？

> Producer 使用合适 acks、retry、幂等与副本配置；Broker 配 replica/min ISR 和可靠存储；Consumer 业务成功后提交 offset、失败重试并告警。数据库双写还需 Outbox，外部副作用还需幂等和对账。当前 Catalog 与 Payment → Order 都把这些机制落到持久化 Inbox/Outbox、worker、版本 fence 和对账；没有一个开关能单独保证端到端不丢。

### 39. Kafka 为什么会重复消费？

> 业务成功但 offset 未提交就崩溃、rebalance、超时或 producer retry 都可能导致重复观察。采用 at-least-once 时必须以 event ID、唯一约束和事务内 processed record 保证幂等。

### 40. Kafka 的 Exactly-once 是什么范围？

> Kafka 幂等 producer 避免单 producer retry 重复写；transaction 可原子发布 Kafka 记录并提交消费 offset。它不自动包含 PostgreSQL、MongoDB、Stripe 或邮件，因此端到端仍需 Outbox/Inbox、幂等 key 和状态机。

### 41. `fromBeginning: true` 有什么影响？

> 仅当 group 没有已提交 offset 时从最早开始；已有 offset 仍从 offset 继续。生产误用新 group ID 会重放历史，所以消费者必须幂等，并对 group/offset 变更做发布管控。

### 42. Retry Topic 与 DLQ 有什么问题？

> 它们让主消费不被毒消息永久阻塞，但可能破坏实体顺序，并需要告警、修复和安全重放。DLQ 是运维流程，不是垃圾桶；永久 schema 错误不该无限 retry。

### 43. 什么是 Outbox？

> 在同一数据库事务写业务记录与待发布事件，由 worker/CDC 可靠发布 Kafka。它消除 DB 成功但事件永久未记录的窗口；Publisher 仍可能重复发送，所以 Consumer 仍需幂等。当前项目创建/更新/删除商品时同时写 `ProductOutboxEvent`；Payment 状态更新同时写通用 `PaymentOutboxEvent`；Order 投影和 Ack `OrderOutboxEvent` 在同一 Mongo transaction 提交。

## 七、Redis

### 44. Cache Aside 如何工作？

> 读先缓存，miss 查 DB 并回填；写先更新 DB 再删除缓存。它是最终一致，不是强一致；TTL、失效重试、版本和关键读绕缓存用于控制风险。

### 45. 穿透、击穿、雪崩区别？

> 穿透是不存在 key 持续回源；击穿是单热点 key 过期并发回源；雪崩是大量 key 同时失效或 Redis 故障。分别用空值/Bloom/限流、singleflight/逻辑过期、TTL 抖动/高可用/熔断降级。

### 46. Redis 单线程为什么还能快？

> 核心操作主要在内存，数据结构高效，事件驱动 I/O 减少等待和共享锁竞争；但现代 Redis 也有 I/O/后台线程。慢命令、大 key、网络、序列化和持久化仍会造成长尾。

### 47. Redis 分布式锁有哪些坑？

> 锁必须 NX + TTL + 唯一 token，释放要比较 token；要考虑任务超时、续期、进程暂停、网络分区和主从切换。关键写使用 fencing token 和数据库约束，不能把锁当绝对一致性保证。

### 48. 本项目优先在哪使用 Redis？

> 第一是经指标证明有收益的公共商品详情/列表缓存；第二是搜索、Checkout 等分布式限流；第三是后台统计短缓存。支付事件的持久化 Inbox 和数据库唯一约束必须保留，Redis 不能替代它们。每项都要明确 key、TTL、失效、降级和权威数据源。

## 八、支付与系统设计

### 49. 为什么不能信任前端购物车价格？

> 浏览器数据可修改且可能过期。当前支付服务按 product ID 读取 Payment DB 中版本已确认的 Stripe Price ID，校验所选 size/color 与正整数数量，按服务端快照计算金额；缺失或未同步时返回 `409 CATALOG_SYNC_PENDING`。下一步还需要 SKU 库存、预占和业务数量上限。

### 50. Stripe Webhook 为什么需要验签和幂等？

> 验签证明请求由 Stripe 持有 secret 的系统生成且 body 未被改；Stripe 会重试，网络也可能重复，所以还要按 event ID 唯一去重。当前 handler 验签后先写 `StripeWebhookInboxEvent` 才返回 200，数据库失败返回 500 让 Stripe 重试；业务状态和 Kafka Outbox 由独立 worker 在同一事务完成。验签不等于只收到一次。

### 51. 请求超时是否等于操作失败？

> 不等于。服务或第三方可能已完成副作用，只是响应丢失。写操作要用 idempotency key，客户端查询权威状态；系统保存 operation ID/状态并通过异步事件和对账收敛。

### 52. 如何设计可观测性？

> 日志包含 request/trace/correlation ID 和结构化错误；指标用 RED/USE 加支付成功率、订单差值、Kafka lag；trace 跨 HTTP/Kafka 传播；告警面向用户影响和可行动阈值。敏感信息必须脱敏。

### 53. 如何应对下游服务不可用？

> timeout 是第一步；读可降级/缓存，写需幂等后有限 retry；持续故障用 circuit breaker 和 bulkhead；异步任务进入 retry/DLQ；状态显示处理中；最后依靠对账恢复，不隐藏失败。

### 54. 这次商品目录可靠同步是否实现了 Exactly-once？

> 没有承诺跨 Product PostgreSQL、Kafka、Payment PostgreSQL 和 Stripe 的 exactly-once。实现目标是持久化 at-least-once 与最终一致：Product 业务数据和 Outbox 同事务；Payment 用 Inbox event ID 去重并按版本更新 ledger；Stripe 请求使用包含 productId、version、operation、同步 run ID 和具体动作的幂等键；结果用条件更新和结果 Outbox 回传；定时对账修复未知结果与漂移。即使 worker 在外部成功后、数据库确认前崩溃，也可以在同一轮同步中安全重做操作。

**Update · 2026-09-26 · 追问“对账自身会不会误操作？”：** 不能只用对账开始时的账本快照判断孤儿。当前归档前及每次 Stripe 写入前都查询实时账本；写入过程中商品变成已知时，用 mutation fence 和事务结果 Outbox 安排修复。默认 Price 的 ID 也与账本比较，相同金额但换了 Price 仍算漂移。检查与 Stripe 写入不是原子事务，最终一致仍靠修复和周期性对账。

### 55. Product 的同步状态是 `SYNCED`，为什么 Checkout 仍可能返回 409？

> 展示和结算是两个独立边界。Product 的结果消费者按当前版本和结果 revision 更新 `stripeSyncStatus`；Checkout 则直接检查 Payment DB 的 `StripeCatalogItem` 是否 `SYNCED`、已应用版本是否等于期望版本，以及 Stripe Price ID 是否存在。目录传播或对账期间两边可能暂时不同；不能用商品页面可见性代替结算校验。看 `product.controller.ts` 和 `checkoutCatalog.ts`。

### 56. 用户重复点击结算，或 Stripe 成功创建 Session 后服务崩溃，会怎样？

> 前端在 `sessionStorage` 保留同一购物车请求的 UUID；Payment 用 `(userId, clientRequestId)` 唯一约束和请求指纹固定一个 `CheckoutAttempt`，相同 key 对不同请求返回冲突。Stripe Session 使用由 attempt ID 派生的幂等键；如果外部创建成功但本地尚未确认，重试和对账会尝试恢复，不把请求超时当成未创建。看 `StripePaymentForm.tsx`、`checkoutSession.ts`、`paymentReconciliation.ts`。

**Update · 2026-09-26 · 追问“Session 过期怎么办？”：** 复用本地已确认 Session 前，Payment 向 Stripe 查询状态。`open` / `complete` 返回原结果；只有 `expired` 返回 `409 CHECKOUT_SESSION_EXPIRED`。Client 创建替换请求 key、新的 attempt，最多自动多请求一次；并发过期响应共享替换 key，旧购物车响应不会覆盖新购物车 key。超时、查询失败或完成的 Session 都不触发自动换键。这不代表超过 Stripe 幂等保留边界的未知创建结果已经能安全恢复，该问题仍待实现。

**Update · 2026-09-26 · 测试边界：** Client helper 的 receiver-sensitive fake 已覆盖原生 `fetch` 被错误绑定时的回归。Node fake 测试、真实数据库事务测试和 Stripe Test Mode/浏览器冒烟各验证不同边界，不能互相替代；退款失败/取消的完整处理也不能列为已完成成果。

### 57. Webhook 返回 200 后 worker 失败，为什么事件还在？

> HTTP 路由验签后先按 Stripe `event.id` upsert 到 `StripeWebhookInboxEvent`，持久化失败返回 500。返回 200 只表示“已安全接收”，不表示订单已经建好。独立 worker 使用 lease、有限重试和失败状态处理；支付状态与 Payment Outbox 同一事务，Order 端再通过 Inbox、事务和 Ack 确认。看 `webhooks.route.ts` 与 `stripeWebhookWorker.ts`。

### 58. 为什么支付成功时商城仍可能显示“正在创建订单”？

> Payment 的 `SUCCEEDED` 只说明支付账本已更新。生命周期事件还要经 Payment Outbox、Kafka、Order Inbox/Mongo 事务和 Ack 回到 Payment。`GET /sessions/:session_id` 仅在 `orderExists=true` 且 `orderAppliedVersion === version` 时返回 `CONFIRMED`；返回页轮询期间保留购物车，确认后才清空。看 `session.route.ts` 和 `PaymentReturnStatus.tsx`。

### 59. 失败支付事件会直接创建一个 failed Order 吗？

> 不会。Order 的 `decideOrderProjection` 在没有现存订单且快照支付状态不是 `SUCCEEDED` 时不创建 Order，但 worker 仍在同一 Mongo transaction 完成 Inbox 并写 `orderExists=false` Ack。成功订单后续收到更新版本的退款或争议快照时才更新已有投影；旧版本被忽略。

### 60. 消费到坏消息或数据库暂时不可用时，当前处理是否一样？

> 不一样。当前订阅显式用 `errorPolicy: 'retry'`：合法消息写 Inbox 失败会抛错，避免自动提交 offset。Order 的坏 JSON/坏契约被写入 `RejectedPaymentEvent` 后跳过，留存失败仍会重试；Payment 侧已解析但无效的 Catalog/Ack 载荷主要记日志后跳过，目录 topic 的无法解析 JSON 则会重试并可能阻塞分区。未来要补统一的坏消息隔离、告警、契约检查和受控重放，不能笼统说已有 DLQ。

## 九、面试中的危险说法

避免以下表达：

- “Next.js 的 fetch 默认都会缓存。”
- “JWT 是加密的，所以能放敏感信息。”
- “用了 Kafka 就不会丢消息/保证一致性。”
- “Kafka 开 exactly-once，数据库也只会写一次。”
- “Redis 是单线程，所以没有并发问题。”
- “加分布式锁就绝对不会超卖。”
- “MongoDB 没事务”或“有事务所以随便建模”。
- “微服务一定比单体高级。”
- “用了 Clerk，后端就不用鉴权。”
- “用了 ORM 就不需要 SQL。”

更好的句式：

> 在当前约束下我选择……；它解决了……，代价是……；当前项目做到……，生产环境下一步会……；最终通过……验证。
